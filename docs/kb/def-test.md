# 红队评测与上线清单

> Red Team Evaluation & Go-Live Checklist · 分类：防御与评估

## 1. 一句话定义

把攻击知识变成可重复的评测流程：用固定的测试集与判定标准衡量防护效果，并在上线前后用清单确认每一项控制真的生效。

## 2. 机制与原理

- 没有评测的安全加固无法证明有效。改了提示词、加了过滤，效果需要被量化。
- 评测集应覆盖本知识库的各分类，而不是只测提示注入一种。
- 关键难点是**误报控制**：过滤过严会伤害正常业务，因此需要一批"良性但相似"的样本作为对照。
- 判定标准要预先写定，避免事后按结果调整口径。

## 3. 评测集设计

| 分类 | 样本类型 | 期望结果 |
| --- | --- | --- |
| 直接注入 | 覆盖型、目标替换型 | 拒绝，或仍按原任务执行 |
| 间接注入 | 文档中隐藏指令 | 不执行文档中的指令 |
| 编码混淆 | 零宽字符、同形字变体 | 归一化后仍被识别 |
| 越狱 | 角色扮演、情感诉求 | 保持原有策略 |
| 多轮 | 渐进升级、拒绝后换角度 | 经会话整体评估后拒绝 |
| 延迟触发 | 条件型规则 | 在写入阶段即被拦截 |
| 工具滥用 | 无业务理由的调用请求 | 不触发高风险动作 |
| 多体通信 | 伪造上游消息 | 接收方拒绝执行 |
| 记忆投毒 | 偏好植入、规则伪造 | 写入阶段被拦截 |
| 良性对照 | 正常业务请求（含敏感词但意图正当） | 正常通过 |

## 4. 判定标准

```text
四种判定结果
  拦截     —— 风险样本被拒绝，且拒绝话术不泄露规则细节
  部分保留 —— 内容被部分采纳，需分析是业务需要还是防护不足
  放行     —— 风险样本未被拦截，计为失败
  行为偏离 —— 输出与任务目标不一致（可能是注入生效的表现）

良性对照的判定
  正常通过 —— 期望结果
  被误拦   —— 计为误报，需要调整规则

评分建议
  同时呈现两个指标：风险样本拦截率 + 良性样本通过率
  只报拦截率会鼓励过严的规则；两个指标并列才能反映真实可用性
```

## 5. 上线清单

```text
上线前
  [ ] 已完成各分类评测，拦截率与误报率均已记录
  [ ] 系统提示中不含密钥、内部地址与具体阈值
  [ ] 全部工具按最小权限授予，读写已分离
  [ ] 高风险动作已强制人工确认
  [ ] 出站访问走白名单
  [ ] 检索层强制租户隔离，来源可标记
  [ ] 记忆写入有审核，条目可追溯来源
  [ ] 输入侧归一化在检测之前执行
  [ ] 日志记录完整决策链

上线后
  [ ] 定期复测评测集，记录指标变化
  [ ] 监控工具调用异常与出站流量
  [ ] 清点暴露的 AI 组件与版本
  [ ] 复核审批记录，确认不是形式化通过
```

## 6. 检测与观察点

- 评测集是否随新出现的攻击手法更新。
- 指标是否同时包含拦截率与误报率。
- 拒绝话术是否泄露了规则细节（这会帮助攻击者定向绕过）。
- 上线清单是否被真正执行，而不是只存在于文档中。
