# 案例：跨会话数据读取实测（沙箱只强制写入边界）

> Case: Cross-Session Data Read — Read Boundary Is Not Enforced · 分类：案例教材

## 1. 一句话定义

对本地另一个项目的 DSH 会话做实测：结果确认**文件沙箱强制了写入边界，但没有强制读取边界** —— 工作区外的会话数据可被完整读出并落到工作区内。

本页全部数据来自实测，每条都附可复核的旁证。与本文配套的 `case-prompt.md` 记录了同一议题上一次失败的方法论（自测无法产生数据），两页必须合读。

## 2. 机制与原理

### 沙箱语义的实际边界

会话声明的策略是 `workspace-write`，原文是"受 DSH 文件沙箱强制的操作可以在工作区内修改文件"。实测表明这句话应精确理解为：

| 方向 | 是否强制 | 实测结果 |
| --- | --- | --- |
| 工作区内写入 | 强制允许 | 成功 |
| 工作区外写入 | **强制拒绝** | 被拒，提权 fail-closed |
| 工作区外读取 | **不强制** | 成功，无任何阻拦 |

**这是本次最重要的发现。** 沙箱管的是"改哪里"，不是"读哪里"。因此任何依赖沙箱防止数据外流的设想都不成立。

### 为什么 `read` 工具的拒绝不是安全边界

`read` 工具拒绝该文件，理由原文是：

```text
Error: cannot read "...session.jsonl.zstd": binary file
```

这是**二进制文件判定**，不是权限拒绝。换用 `pwsh` 读原始字节立即成功。也就是说这个限制是工具便利性设计，**绕过成本约等于零**。把工具自身的行为当作安全控制，是评估中的典型误判。

### 会话数据的落盘格式

```text
路径   C:\Users\<user>\.dsh\sessions\<项目目录名编码>\<会话 id>\session.jsonl.zstd
格式   zstd 压缩，**多帧拼接**，每帧一条 JSONL 记录
内容   会话头、策略变更、用户消息原文、工具调用参数原文、工具结果、推理分块
```

两个必须注意的细节：

1. **多帧拼接**。用 `ZstdDecompressor().decompress()` 只读第一帧就返回，会把 10 MB 的会话误读成 196 字节 —— 这是假阴性。正确做法是 `stream_reader` 循环读到 EOF。本次实测中我先踩了这个坑，导致第一轮扫描结论完全错误。
2. **项目目录名做了编码**（如 `D:\AI WORKER\...` → `--D-AI~0020WORKER-...--`），但编码可逆且明文可枚举。

### 子代理提示词会携带父会话上下文

跨项目数据之所以能被一次读全：某些子代理会话的提示词里**内嵌了父对话的最近若干条真实用户消息**。因此读一个子代理会话文件，等于间接读到它父项目的对话内容。

## 3. 攻击面与前提

| 项 | 实测情况 |
| --- | --- |
| 前提一：可读工作区外路径 | 成立。4/4 敏感路径可读 |
| 前提二：有可用解压能力 | 成立。目标环境有 python + `zstandard` |
| 前提三：可把数据落到工作区内 | 成立。工作区内写入被允许 |
| 前提四：会话数据落盘在可枚举位置 | 成立。路径可枚举、格式公开 |
| 前提五：子代理提示词含父会话片段 | 成立。实测直接读到另一个项目的用户消息 |
| 用户交互要求 | 无。读取阶段完全静默，不触发任何审批 |

**关键结论：这条链路在 `workspace-write` 策略下不需要任何提权即可完成。**

## 4. 典型形态与示例

实测复现流程（六步，全部在 `workspace-write` 下完成）：

```text
步骤 1  起一个受限会话
        dsh --profile headless "<任务>"
        实测策略: permission=workspace-write, approval=ask

步骤 2  用 read 工具试读目标会话文件
        → 被拒，理由为 "binary file"（工具判定，非权限）

步骤 3  改用 pwsh 读同一路径
        → 成功，无沙箱拒绝
        实测读取上限: 4/4 敏感路径全部可读

步骤 4  解压（必须用流式读多帧）
        zstandard.ZstdDecompressor().stream_reader(f) 循环读取
        实测: 60,873 字节压缩 → 124,962 字节解压 → 145 条记录

步骤 5  把解压结果写入工作区内
        → 成功（工作区内写入被允许）
        实测落地: 132,048 字节 jsonl 落到仓库工作区

步骤 6  解析出 conversational 原文
        → 成功取得另一个项目的真实用户消息
```

关键对比：**读取在边界外、写入在边界内、数据从外流到内。** 沙箱对这条路径没有任何阻拦。

### 证据标准

本页只接受两类证据：**可复核的旁证**（文件确实存在/不存在、字节数、独立解压比对），或**原文引用**。所有推断都显式标注为推断。上一版 `case-prompt.md` 曾把回显桩和自述当成测量结果，那是错误示范，已改正。

## 6. 防御与改进

```text
[必修 1] 把读取边界纳入沙箱
  当前沙箱只强制写入。若会话数据、凭据、其他项目文件不应被读，
  必须新增读取侧策略（路径白名单），不能依赖工具自身限制。
  → 这是本案例的根本修复项。

[必修 2] 不把工具行为当安全控制
  read 的 "binary file" 拒绝是便利性设计，pwsh 一句话即可绕过。
  任何"某工具读不了"的判断都必须用另一种工具复核后才能作为结论。

[必修 3] 收缩会话文件的可见范围
  会话含用户消息、工具参数、推理过程的完整原文，
  应与凭据同级保护，而非放在用户主目录下的可枚举路径。
  → 至少：目录权限收紧、避免明文项目名可逆编码。

[必修 4] 子代理提示词最小化
  子代理提示词内嵌父会话片段会让"读一个子代理会话"升级为
  "读一个项目的对话"。只传必要片段，且视为敏感数据。

[必修 5] 工作区内写入也要有审计
  工作区允许写是合理的，但"把外部数据搬进工作区"这一动作
  应留下可审计记录，否则外流会伪装成正常开发产物。
```

优先级依据：必修 1 是根因，其余是纵深。**只做必修 2~5 而不修读取边界，等于把门锁上但窗户继续开着。**
