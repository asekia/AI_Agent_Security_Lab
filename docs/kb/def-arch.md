# 架构侧防御

> Architecture-Side Defenses · 分类：防御与评估

## 1. 一句话定义

把安全约束从提示词搬进系统结构：最小权限、执行隔离、出站管控与人工审批，让"模型被骗"不再直接等于"攻击成功"。

## 2. 机制与原理

- 提示词层面的防护会被绕过。架构层面的约束不会被"说服"，只会被违反——而违反会触发拒绝。
- 核心思路是把模型的判断与真实副作用解耦：模型可以提出请求，但是否执行由外部系统决定。
- 四类结构性控制：
  1. **最小权限**：工具只拥有当前任务所需的最小能力。
  2. **执行隔离**：代码执行发生在沙箱内，与生产环境分离。
  3. **出站管控**：外部访问走白名单，目标地址不由模型决定。
  4. **人工审批**：高副作用动作必须有人确认。

## 3. 攻击面与前提

| 控制项 | 解决的问题 | 失效后果 |
| --- | --- | --- |
| 最小权限 | 工具误用与越权 | 一次错误判断造成真实损失 |
| 执行隔离 | 意外代码执行 | 沙箱逃逸影响宿主环境 |
| 出站管控 | 数据外带 | 敏感内容被发送到外部地址 |
| 人工审批 | 人机信任滥用 | 高风险动作被形式化通过 |

## 4. 典型形态与示例

```text
按副作用分层（概念演示）
  只读动作（查询、检索）          → 自动执行
  低风险写入（草稿、标记）        → 自动执行并记录
  高风险动作（发送、删除、付款）  → 强制人工确认，展示完整参数
  执行类动作（代码、命令）        → 沙箱内执行，网络与文件系统受限

纵深布置
  输入侧过滤 → 提示边界声明 → 工具权限最小化 → 参数校验
  → 出站白名单 → 人工审批 → 事后审计
  任何一层失效时，其他层仍然有效
```

## 5. 检测与观察点

- 权限是否由外部系统强制，还是仅写在提示词里。
- 高风险动作是否存在可绕过的路径（直接调用工具、跳过审批）。
- 出站请求是否全部经过统一出口。
- 沙箱是否真的限制了网络与文件系统，而不只是名义上的隔离。
- 审批记录能否回答"谁批准了什么"。

## 6. 防御与改进

- 按最小权限重构工具集，把"读"与"写"拆开。
- 高副作用动作强制人工确认，并在确认界面展示参数与影响范围。
- 出站访问走统一出口与白名单，禁止由模型指定目标地址。
- 执行类能力放进沙箱，限制网络与文件系统访问范围。
- 审计日志记录完整决策链：输入摘要、检索来源、工具参数、审批人。
