# 上下文窗口溢出

> Context Window Overflow · 分类：上下文与记忆攻击

## 1. 一句话定义

利用上下文窗口的容量上限：灌入超长内容，把早期的安全指令挤出窗口，使模型在后续轮次中不再受最初的约束。

## 2. 机制与原理

- 上下文窗口存在硬上限。当内容超出时，系统必须丢弃部分历史。
- 常见实现采用 FIFO（先进先出）：最早的内容最先被丢弃，而系统提示通常就位于最前面。
- 于是"先灌够内容，再提问"成为一种绕过手段：等约束被挤出窗口，攻击才真正发生。
- 与注入的区别在于：注入是**改变**指令内容，溢出是让指令**消失**。两者常被组合使用。
- 这条路径同时带来资源问题，与本项目的 ASI08（级联故障）与 ASI10（无限制消耗）相关。

## 3. 攻击面与前提

| 项 | 内容 |
| --- | --- |
| 入口 | 对话输入、超长文档、批量工具返回 |
| 成立前提 | 上下文按 FIFO 截断；窗口大小有限；缺少输入长度限制 |
| 观察点 | 会话轮次较多后行为异常；早期约束不再被遵守 |
| 影响 | 安全指令被挤出窗口，后续行为失去约束 |

## 4. 典型形态与示例

```text
1. 铺垫式溢出
   先提交大量看似正常的长文本（日志、文档、代码），占满窗口
   待早期指令被丢弃后，再提交真正的越权请求

2. 单条超长输入
   一条消息就超过窗口上限，使系统提示在第一轮即被截断

3. 工具返回放大
   让工具返回超长结果，用工具输出挤占窗口空间

4. 长文档检索
   检索大量片段填满上下文，使安全说明不再位于窗口之中
```

## 5. 检测与观察点

- 单会话的上下文长度增长是否异常。
- 从某一轮开始，输出风格与约束遵守情况是否发生突变。
- 是否存在无业务理由的超长输入或超长工具返回。
- FIFO 截断是否有日志记录，能否事后确认"哪一轮丢掉了什么"。

## 6. 防御与改进

- 限制单条输入长度与单会话总长度。
- 关键安全约束不要只依赖上下文开头：每一轮重新注入，或落到代码层的策略检查里。
- 截断时优先丢弃低价值内容，保留系统提示与安全策略。
- 对上下文长度的异常增长做监控与告警。
