# 输出处理型攻击

> Improper Output Handling · 分类：提示注入体系

## 1. 一句话定义

攻击的落点不在模型，而在下游：模型输出被未加校验地送进 HTML、SQL、Shell、模板或另一个模型，于是"文本"变成了"可执行的东西"。

## 2. 机制与原理

- 模型输出本质上是文本，但下游组件可能赋予它语义：浏览器执行、数据库解析、操作系统执行、模板引擎求值。
- 注入的最终目标常常不是让模型"说错话"，而是让它生成一段会被下游执行的字符串。
- 这与经典的 XSS、SQL 注入、命令注入同源，区别只是污染源从用户输入变成了模型输出。
- 危险之处在于：开发者容易认为"模型输出是我们自己系统产生的，可以信任"。
- 对应风险：OWASP LLM05 Improper Output Handling。

## 3. 攻击面与前提

| 项 | 内容 |
| --- | --- |
| 入口 | 模型输出的消费方：前端渲染、SQL 拼接、Shell 调用、模板引擎、下游模型 |
| 成立前提 | 输出未经过与用户输入同等级别的校验 |
| 观察点 | 输出中的 HTML 或脚本片段、SQL 关键字、Shell 元字符、模板语法 |
| 影响 | XSS、SQL 注入、远程代码执行、越权访问 |

## 4. 典型形态与 payload

```text
1. 前端渲染
   让回答中包含 <img src=x onerror=alert(1)>，前端未转义即执行

2. SQL 拼接
   让模型在"客户名称"字段位置输出 ' OR 1=1 --

3. Shell 调用
   让模型输出 $(whoami) 并被拼接进命令行

4. 模板注入
   让模型输出 {{7*7}}，服务端模板引擎对其求值

5. 二次模型投毒
   上游模型的输出直接作为下游模型的输入，中间不做隔离与校验
```

### 一个完整的前端载荷链路

```text
1. 攻击者通过间接注入让模型在回答中输出：
   <iframe src=my-account onload=this.contentDocument.forms[1].submit()>

2. 前端把回答原样渲染成 HTML（漏洞前提：LLM05 Improper Output Handling）

3. 受害者浏览器解析 iframe → onload 触发 → 自动提交表单
   —— 例如"确认转账""修改邮箱"一类的状态变更操作
```

要点：模型在这里扮演的是"反射点"——恶意 JavaScript 不经过服务端校验，因为它是从模型输出流进前端的。输出侧的净化责任在渲染端，但防线要提前到"模型输出进入 HTML 上下文之前"。

## 5. 检测与观察点

- 输出是否直接进入危险上下文：有无编码、转义或参数化。
- 是否存在输出结构校验：schema、类型、长度、允许值范围。
- 前端是否使用 `innerHTML` 一类的危险赋值方式。
- 输出被用于拼接查询或命令的位置是否有集中的安全封装。

## 6. 防御与改进

- 对模型输出采用与用户输入相同（或更严格）的校验标准。
- 数据库访问使用参数化查询，命令调用避免字符串拼接，输出按上下文转义。
- 前端用文本节点赋值替代 HTML 注入点。
- 用结构化输出约束（如 JSON schema）限制模型输出的形态与字段。
- 在模型与下游系统之间保留一道显式的校验与清洗层。
