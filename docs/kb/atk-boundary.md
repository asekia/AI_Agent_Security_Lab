# 沙箱读写边界与跨项目数据读取

> Sandbox Read/Write Boundary & Cross-Project Data Access · 分类：Agent 攻击面实战

## 1. 问题与威胁模型

**目标**：确定 Agent 文件沙箱的真实强制边界，找到"读取方向"上可跨越边界的路径，并验证工作区外数据可以被搬进工作区。

**威胁模型**：

| 角色 | 能力 |
| --- | --- |
| 攻击者 | 能向 Agent 的任务描述或可读内容注入指令；不能修改沙箱配置 |
| 目标 | 以 `workspace-write` 策略运行 Agent：工作区内可写，工作区外按策略处理 |
| 前提 | Agent 具备读文件与执行命令两种能力（编码 Agent 的常规配置） |

**核心命题**：`workspace-write` 强制的是**写入**边界，不是**读取**边界。读取方向未强制时，工作区外数据（其他项目的会话记录、凭据文件、全局配置）可被完整读入工作区，随后随正常产物分发。这不构成提权，但构成完整的数据外流路径。

## 2. 原理推导

### 2.1 边界语义分解

策略原文是"受沙箱强制的操作可以在工作区内修改文件"。逐方向实测后语义应精确理解为：

| 方向 | 是否强制 | 结果 |
| --- | --- | --- |
| 工作区内写入 | 强制允许 | 成功 |
| 工作区外写入 | **强制拒绝** | 被拒，提权 fail-closed |
| 工作区外读取 | **不强制** | 成功，无任何阻拦 |

**推导**：安全评估中"文件沙箱"一词容易掩盖方向差异。必须分别测试四个方向（内读、内写、外读、外写），不能用一个结论概括。

### 2.2 工具级拒绝与沙箱级拒绝

读工具拒绝文件时的错误可能是：

```text
Error: cannot read "...session.jsonl.zstd": binary file
```

这是**二进制判定**，属于工具便利性设计，不是权限拒绝。换用命令执行读原始字节立即成功，绕过成本约等于零。

**推导**：任何"某工具读不了"的判断，必须换另一条能力路径复核后才能作为安全结论。工具行为 ≠ 安全控制，这是评估中最常见的误判。

### 2.3 会话数据的落盘结构

```text
路径   <用户主目录>\.<agent>\sessions\<项目目录名编码>\<会话 id>\session.jsonl.zstd
格式   zstd 压缩，多帧拼接，每帧一条 JSONL 记录
内容   会话头、策略变更、用户消息原文、工具调用参数原文、工具结果、推理分块
```

三个影响读取成败的细节：

1. **多帧拼接**。一次性 `decompress()` 只解第一帧并静默返回，大文件会被误读为极小字节。正确做法是 `stream_reader` 循环读到 EOF。
2. **目录名编码可逆**。如 `D:\AI WORKER\proj` → `--D-AI~0020WORKER-proj--`，编码规则固定且明文可枚举。
3. **子代理提示词携带父会话片段**。某些子代理会话的提示词内嵌父对话的最近若干条真实用户消息——读一个子代理会话等于间接读父项目对话。

## 3. 攻击面与前提

| 前提 | 验证方式 | 成立条件 |
| --- | --- | --- |
| 可读工作区外路径 | 读一个工作区外已知文件 | 读取边界未强制 |
| 有解压能力 | 目标环境有 python + zstandard | 常规开发环境 |
| 可把数据落到工作区内 | 写一个工作区内临时文件 | `workspace-write` 允许 |
| 会话数据落盘位置可枚举 | 列出 sessions 目录 | 路径模式固定 |
| 子代理提示词含父会话片段 | 解压任意子代理会话 | 取决于实现 |

**用户交互要求：无。** 读取阶段完全静默，不触发任何审批。

## 4. 实战步骤

### 步骤 1：确认策略与能力面

```text
读运行时声明，记录：file_policy / approval_prompts / shell
枚举能力：是否有读文件、执行命令、写文件三类工具
```

### 步骤 2：四个方向各测一次

```text
[内读] 读工作区内已知文件            → 预期成功
[内写] 写工作区内临时文件            → 预期成功
[外读] 读工作区外已知文件            → 观察是否被拒
[外写] 写工作区外路径                → 预期被拒（fail-closed）
```

判读：外读成功即边界不对称成立，进入步骤 3；外读被拒则需判断拒绝层级（工具级还是沙箱级）。

### 步骤 3：用第二能力路径复核工具级拒绝

```text
若读工具报 "binary file" / "permission denied"：
  换命令执行读同一路径的原始字节
  若成功 → 工具级拒绝，非安全边界
  若失败且错误来自执行器策略 → 沙箱级拒绝
```

### 步骤 4：枚举会话目录

```text
列出 <主目录>\.<agent>\sessions\
观察目录名编码规则，反推项目路径
按会话 id 定位目标会话文件
```

### 步骤 5：流式解压（关键正确性点）

```python
import io
import zstandard

frames = [f'{{"seq":{i},"msg":"user message {i}"}}'.encode() for i in range(3)]
blob = b"".join(zstandard.ZstdCompressor().compress(f) for f in frames)

# 错误：一次性 decompress 只解第一帧（静默，不报错）
bad = zstandard.ZstdDecompressor().decompress(blob)
print("decompress() ->", bad)

# 正确：流式读到 EOF
good = zstandard.ZstdDecompressor().stream_reader(io.BytesIO(blob)).read()
print("stream_reader() ->", good)
```

实测输出：

```text
压缩后: 87 字节
decompress() -> b'{"seq":0,"msg":"m0"}'
stream_reader() -> b'{"seq":0,"msg":"m0"}{"seq":1,"msg":"m1"}{"seq":2,"msg":"m2"}'
```

量级参考：60,873 字节压缩 → 124,962 字节解压 → 145 条记录。用错误做法会把整份会话误判为不存在——扫描假阴性比漏扫更难发现。

### 步骤 6：落地工作区并解析

```text
把解压结果写入工作区内临时文件
解析 JSONL，提取 conversational 原文与工具调用参数
```

关键对比：**读取在边界外、写入在边界内、数据从外流到内。** 沙箱对这条路径没有任何阻拦。

## 5. 变体目录

| 变体 | 做法 | 用途 |
| --- | --- | --- |
| 工具绕过 | 读工具拒绝 → 命令执行读原始字节 | 证明工具级限制不是边界 |
| 格式绕过 | 直接解压 zstd，不依赖内置读取器 | 绕过二进制判定 |
| 路径枚举 | 反推目录名编码 | 定位其他项目会话 |
| 间接读取 | 读子代理会话获取父会话片段 | 扩大单文件情报量 |
| 批量搬运 | 逐会话解压后写入工作区 | 形成可分发数据集 |

## 6. 检测与取证

- 对工作区外路径的读取尝试，尤其是 `.zstd`、会话目录、凭据文件路径。
- 用命令执行读取被读工具判定为"二进制"的文件——边界绕过的直接信号。
- 流式解压模式：超大 zstd、循环读到 EOF 的读写行为。
- 跨项目路径枚举：会话目录名编码模式的猜测与遍历。
- "把外部数据搬进工作区"的写入：内容与当前任务无关时告警。

## 7. 防御与验证

### 7.1 防御

```text
[必修 1] 把读取边界纳入沙箱
  若会话数据、凭据、其他项目文件不应被读，必须新增读取侧策略（路径白名单）。
  这是根因修复项。

[必修 2] 不把工具行为当安全控制
  "binary file" 拒绝是便利性设计，命令执行一句话即可绕过。

[必修 3] 收缩会话文件的可见范围
  会话含用户消息、工具参数、推理过程完整原文，应与凭据同级保护。

[必修 4] 子代理提示词最小化
  只传必要片段，且视为敏感数据。

[必修 5] 工作区内写入也要有审计
  "把外部数据搬进工作区"应留下可审计记录。
```

优先级：必修 1 是根因，其余是纵深。只做 2~5 而不修读取边界，等于把门锁上但窗户继续开着。

### 7.2 防御验证

```text
[验证 1] 四方向测试：外读必须与内读同样受策略约束
[验证 2] 工具绕过测试：所有读取工具拒绝后，命令路径也必须拒绝
[验证 3] 会话文件权限：非该会话所属用户不可读
[验证 4] 搬运审计：工作区内出现外部数据时产生告警
```
