# 已知 CVE 速查

> Known CVE Reference · 分类：AI 基础设施与供应链

## 1. 一句话定义

AI 基础设施组件的公开漏洞速查。推理框架与 MLOps 平台的已知问题，是"服务暴露即被利用"的主要来源。

## 2. 机制与原理

- AI 基础设施组件的更新节奏通常慢于传统中间件，并且常被部署在"内网可信"的假设之下。
- 大量实例沿用默认配置，认证缺失使漏洞利用门槛极低。
- 一旦版本被识别，对照公开公告就能确定可用的攻击面。
- 因此这类问题的处置重点不在"发现"，而在**清点与整改**：知道有哪些组件、是不是受影响版本、有没有对外暴露。

## 3. 使用说明

下表内容来自内部培训笔记的记录。CVE 编号、影响范围与修复版本请以厂商公告与官方漏洞库为准；使用前务必核对当前状态与最新修复版本。

### SGLang

| 编号 | 类型 | 说明 |
| --- | --- | --- |
| CVE-2026-7301 / CVE-2026-7304 | 反序列化 RCE | pickle 不安全反序列化（CERT/CC VU#777338，披露时官方补丁尚有缺口） |
| CVE-2026-7302 | 路径遍历 | 同属 VU#777338 |
| CVE-2026-14890 | 反序列化 RCE | expert-parallel 子系统的 pickle 反序列化（VU#326070），启用该子系统时未认证即可远程代码执行 |
| CVE-2026-3059 / CVE-2026-3060 | 反序列化 RCE | 含多模态组件在内的两处 pickle 反序列化（VU#665416） |
| GHSA-hvwj-8w5g-28rg | 反序列化 RCE | `replay_request_dump.py` 中的不安全 `pickle.load` |

补充两条攻击面特征：

- **默认无认证**：`sglang serve` 不带 `--api-key` / `--admin-api-key` 时所有端点对任何人开放；`/server_info` 曾被发现会把整个 ServerArgs 序列化返回，连 `api_key` / `admin_api_key` 字段一起泄露。
- **反序列化面广**：权重更新、自定义 logit processor、多模态 gen_server、ZMQ 传输层等多条路径都接受 pickle 类格式——任何一条可达即等价于未认证 RCE。

> 更正说明：内部笔记曾将本组问题记为 CVE-2025-69654 至 CVE-2025-69662；经核对公开漏洞库，该编号段属于其他产品。SGLang 相关问题的官方编号以上表为准（CERT/CC VU#777338 / VU#326070 / VU#665416）。

### 平台级事件：Hugging Face Spaces（2024 年 6 月）

攻击者未授权访问 Hugging Face Spaces 平台，读取了开发者存在应用 Secrets 里的认证信息，其中包括可访问私有模型与数据集的 HF 令牌。平台处置与本库"加固清单"完全对应：吊销受影响令牌、建议全部用户迁移到最小范围只读的 fine-grained 令牌、不建议把令牌继续存放在平台 Secrets 中。它与侦察阶段的关系值得记住：GitHub dork 能翻到的 .env 令牌，和平台事件中泄露的令牌，是同一类东西——轮换与缩权是对两头的同一个对策。

| Ollama / vLLM / SGLang 等 | 服务默认无认证直接暴露 | 加认证网关；限制访问来源 |

## 5. 检测与观察点

- 组件版本是否落在受影响范围内。
- 是否仍在沿用默认配置与默认凭据。
- 管理端点与信息端点是否可达，是否需要认证。
- 是否存在与生产无关、但仍在运行的旧版本实例。

## 6. 防御与改进

- 建立组件与版本清单，订阅对应厂商的安全公告。
- 默认凭据与默认配置在部署前统一整改，并纳入上线检查项。
- 管理面不对外，统一走认证网关。
- 对暴露服务做定期复核，避免"搭完就忘"。
- 修复优先级按"是否对外可达"排序，而不是只按评分排序。
